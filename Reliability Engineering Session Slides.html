// the problem

Two systems, one request, no shared transaction

What everyone writes first

transaction(db) {
  orders.insert(order)
}
sqs.send(OrderCreated(order.id))   // ← here
email.send(confirmation)

The pod dies between the commit and the send: an order with no event, no email, nobody knows. Put the send inside the transaction instead, and the send succeeds, then the commit fails: an event for an order that doesn't exist.

What a request may do

01

Write to the database

One transaction, every table it touches, including a row that says "something else must happen".

02

Respond

The caller gets a 201 as soon as the commit lands. Not when the email went out.

03

Nothing else

No fire-and-forget coroutine, no "best effort" send after commit. If it matters, it is a row; a worker makes it happen.

// the dual write, played out

Four ways a dual write can end. Two of them are bugs.

send succeeds
send fails, or never runs
commit succeeds

Happy path

Order, event, email. The demo always looks like this.

Lost event

An order with no event and no email. Nothing in the logs says so.

commit fails

Ghost event

An email for an order that doesn't exist, if the send went first.

Nothing happened

The client sees an error and retries. Annoying, but honest.

Reordering the two calls only swaps which bug you get. One system has to be the source of truth: the database. That's the outbox.

// idempotency at the edge

The client retries too. Dedupe the request, not only the message.

POST /orders
Idempotency-Key: 9f1c2a…

transaction(db) {
  idempotency.find(orgId, key)?.let {
    return it.storedResponse       // replay
  }
  val order = orders.insert(…)
  outbox.insert("OrderCreated", …)
  idempotency.insert(orgId, key, 201, order)
}

Unique on (org_id, key). Two concurrent duplicates: one commits, the other hits the constraint and returns the stored response.

Why the outbox isn't enough

The mobile client times out at 10 s and retries. The first request did commit. The outbox faithfully records two orders, and the consumer, deduping by event id, happily charges both.

The client sends the key

Generated once per user intent, reused on every retry of that intent. A new key per attempt defeats the point.

Keep it for a while, then expire it

Long enough to cover every client retry window, typically 24 hours. Same cleanup job as the outbox.

hirespartan.io
  • Consumer dedupe by event id protects against SQS redelivery. It does nothing when the API created two different events for one user action.
  • → ×3 reveals the three cards. The next slide plays the retry out step by step.
  • If the stored response could hold sensitive data, store just enough to rebuild it (status + order id).
// the retry, step by step

Same key, same answer: one order, however many retries

hirespartan.io
  • → 1: the first request commits (key, order, outbox in one transaction).
  • → 2: the 201 is lost: the client timed out. From the client's view, nothing happened.
  • → 3: the retry carries the same key; the API finds it.
  • → 4: the stored response is replayed. No second order, no second outbox row.
// the whole pipeline

One durable row in the request, then at-least-once all the way down

① request

Key, order and outbox row in one transaction. Then 201.

② relay

Claim a batch, commit, publish to SQS, mark sent.

③ consumer

Dedupe in processed, work, commit, ack. Then the email.

④ poison message

Fails 5 receives, moves to the DLQ, the alarm pages.

// transactional outbox

Write the event as a row in the same transaction. A relay sends it later.

01 · in the request

One transaction

transaction(db) {
  orders.insert(order)
  outbox.insert(
    type = "OrderCreated",
    payload = json(order.id),
    org_id = order.orgId)
}

Both rows land or neither does.

02 · the relay

Claim, commit, publish, mark sent

-- short tx: claim a batch
UPDATE outbox SET claimed_until = …
… FOR UPDATE SKIP LOCKED
-- commit. no locks held now
-- publish each to SQS
UPDATE … SET sent_at = now()

Runs on every pod. Crash after publish, before the update: the claim expires and it publishes again. At-least-once.

03 · the consumer

Dedupe by event id

transaction(db) {
  if (processed
      .insertIfAbsent(event.id))
    doTheWork(event)
}
ack(message)

The second delivery finds the id and skips. Work and dedupe commit together; the ack comes after.

Delete or archive sent rows on a schedule, or the outbox table becomes the biggest table in the database.

hirespartan.io
  • Three parts, three owners of correctness: the request makes it durable, the relay makes it delivered, the consumer makes it happen once.
  • Next slide zooms into the relay, because that's where the subtle bug lives.
// the relay

Never hold a row lock across a network call. Claim, commit, then publish.

-- 1 · claim (its own short transaction)
UPDATE outbox
   SET claimed_until = now() + interval '30 seconds'
 WHERE id IN (
   SELECT id FROM outbox
    WHERE sent_at IS NULL
      AND (claimed_until IS NULL
           OR claimed_until < now())
    ORDER BY id LIMIT 100
    FOR UPDATE SKIP LOCKED)
RETURNING id, type, payload;
-- commit

-- 2 · publish each to SQS, no locks held
-- 3 · mark what was actually sent
UPDATE outbox SET sent_at = now()
 WHERE id = ANY(:published_ids);

Same rule as the consumer

Holding FOR UPDATE while SQS is slow ties up connections and blocks the cleanup job. The claim column replaces the long lock; an expired claim is how a crashed pod's batch gets picked up.

Order is not preserved

Ten pods publish ten batches in parallel. If order matters, carry a sequence in the payload or use FIFO with a group id.

Polling is a choice

CDC (Debezium, log tailing) is the other relay. More moving parts, lower latency. We poll because it's one table and one loop.

hirespartan.io
  • Walk the SQL top to bottom first. → ×3 reveals the three cards.
  • Claim duration must be longer than the slowest realistic publish of a batch; otherwise two pods publish the same batch more often (still safe, just noisy).
  • Partial batch failure: only mark the ids that were published. The rest wait for the claim to expire.
// lock time, before and after

The slow SQS call no longer sits inside the transaction

Crash right after the claim?

Nothing is lost. The rows stay claimed until claimed_until passes (30 s), then any pod's next poll claims them and publishes again. Consumer dedupe makes the repeat harmless.

// the queue

SQS delivers at least once. Everything else follows from that.

The message

{
  "id": "evt_7c1…",
  "type": "OrderCreated",
  "version": 1,
  "org_id": "org_21a…",
  "occurred_at": "2026-10-10T07:12:00Z",
  "traceparent": "00-4bf9…-01",
  "payload": { "order_id": "…" }
}

An id to dedupe on, a type and version so consumers can evolve, the org so the consumer can scope its queries, the trace context so the trace continues, and ids rather than whole objects: the consumer reads current state from the database.

Four settings that matter

visibility timeout

How long a message is hidden while one consumer works on it. Longer than the work, or a second consumer gets it mid-way.

maxReceiveCount

After this many failed attempts the message moves to the dead-letter queue instead of looping forever.

dead-letter queue

Where poison messages go. Alert when it is not empty; redrive after the fix.

long polling

WaitTimeSeconds 20. Fewer empty receives, lower cost, faster pickup.

hirespartan.io
  • → ×4 reveals the four settings. The next slide shows the first two on a timeline.
  • Standard queues are unordered. If order matters: sequence in payload, or FIFO with a group id, and accept lower throughput.
  • traceparent in the message is what lets one trace span the API and the consumer (slide 24).
// visibility timeout and the DLQ

Too short a timeout: the same message twice. Too many failures: the DLQ.

Set the visibility timeout above the p99 handling time, and dedupe anyway: it will happen during deploys and pauses.

receive 1 ✕→ receive 2 ✕→ receive 3 ✕→ receive 4 ✕→ receive 5 ✕→ orders-dlq · alarm maxReceiveCount = 5
hirespartan.io
  • → 1: consumer A receives the message; it hides for 30 s, but the work takes 45 s.
  • → 2: at 30 s the message is visible again and consumer B takes it. Without dedupe: a second email.
  • → 3: the fix. → 4: a message that always fails: five receives, then the DLQ and the alarm.
// the consumer

Dedupe, do the work, commit, then ack. In that order, every time.

for (msg in sqs.receive(batch = 10)) {
  try {
    transaction(db) {
      if (!processed.insertIfAbsent(msg.id))
        return@transaction
      handle(msg)   // small, scoped by msg.orgId
    }
    sqs.delete(msg)
  } catch (e: Exception) {
    logger.error(e) { "consumer failed id=${msg.id}" }
    // no delete: SQS redelivers after
    // the visibility timeout
  }
}

One bad message must not stop the batch

Catch per message, log with the throwable, move on. The DLQ catches the ones that never succeed.

Keep the transaction small

No outside calls inside it. If handling means calling a vendor, write what you need, commit, then call; or write another outbox row.

Correct with N copies

Ten pods run this loop at once. The dedupe table and the row locks keep them honest, not luck.

Its own executor, its own pool budget

A consumer sharing the API's thread pool starves the API when the queue backs up. Name the executor; count its connections.

hirespartan.io
  • → ×4 reveals the cards. The next slide shows why the order (commit, then ack) matters.
  • Connection budget: API pool + consumer pool + relay pool, per pod, times pod count, must stay under the DB's max connections.
// where can it crash?

Ack first loses work. Commit, then ack, only repeats it.

Crash before the commit: nothing happened, the message runs again. Crash after the commit: dedupe turns the repeat into a no-op. Only ack-first can lose work.

hirespartan.io
  • → 1: ack first. The crash lands between the delete and the work. Gone.
  • → 2: the right order: dedupe and work inside one transaction, then commit.
  • → 3: crash before the ack. SQS redelivers, dedupe finds the id, skips, acks.
  • → 4: the rule. Ask: "Where else could it crash, and what happens?" (before commit: rollback, rerun).
// when a dependency is slow

Timeouts, retries, breakers, bulkheads. Four tools, one goal: fail fast and alone.

A timeout at every hop, each shorter than its caller's

Client waits 10 s; API gives the vendor 3 s; the vendor call gives its connection 1 s. If the inner timeout is longer than the outer, the caller has given up while you are still working for nobody.

Retry with backoff, jitter and a budget

3 attempts, 200 ms × 2ⁿ, random jitter, only on errors that can succeed on retry (timeouts, 503s, not 400s). Only on calls that are safe to repeat.

Circuit breaker: stop calling what's down

After N failures in a window, fail immediately for a cooldown, then let one request through to test. The vendor gets room to recover; your threads aren't tied up waiting.

Bulkhead: a pool per dependency

The vendor call runs on its own small executor. When the vendor hangs, that executor fills up and the rest of the service keeps serving.

Little's law sizes the pools: requests in flight = arrival rate × time per request. 50 req/s at 200 ms each is 10 in flight; a 3 s vendor at the same rate needs 150. That number is why the vendor gets a bulkhead.

hirespartan.io
  • Slow is worse than down: down fails fast on its own, slow holds threads and connections until everything queues behind it.
  • → reveals Little's law. Do the arithmetic out loud; slide 18 lets you play with it live.

// the fine print

Retry in one place, pass the deadline down, and decide what "failing" returns.

Retry amplification

Three layers, each retrying 3 times, turn one user click into 27 calls on a vendor that is already struggling. Retry at one layer, usually the one closest to the dependency.

Propagate the deadline, not a fixed timeout

If the client gave you 10 s and 7 s are gone, the vendor call gets what's left minus a margin, not its usual 3 s. Pass the deadline in a header; check it before each retry.

Decide what failing fast returns

A cached or stale answer, a reduced feature, or "accepted, we'll finish it later" (a 202 and an outbox row). An error is the last option, not the default.

hirespartan.io
  • On entry the fan-out tree grows level by level: 1 → 3 → 9 → 27.
  • → 1: deadlines. → 2: degradation; "accepted, later" connects back to the outbox.
  • Retry budgets help too: allow retries only while they're under ~10% of calls to that dependency.

// backpressure

Say no early: a fast 429 beats a slow yes

p99 latency vs load · illustrative, replace with your k6 run

A queue with no bound grows until the pod runs out of memory. Then everything in it is lost at once.

Bounded executors and bounded queues. When full, reject immediately with 429 or 503 and a Retry-After. A fast no is cheaper for everyone than a slow yes that times out.

Load-test with k6: ramp up, find the point where latency jumps, and name the limit that caused it. That number goes in the runbook.

hirespartan.io
  • → 1: without a limit, latency is flat until the knee, then goes vertical.
  • → 2: name the knee and the resource behind it (here: the DB pool).
  • → 3: with a bound, requests over the limit get a fast 429 and latency for the rest stays flat.
  • Swap the curve for a real k6 run of your service if you have one.
// graceful shutdown

Leave cleanly: every deploy is a shutdown

Anything still running at 30 s is cut off: dropped requests, half-processed messages (dedupe saves you), claims that sit until they expire.

hirespartan.io
  • → 1: SIGTERM. Readiness goes red first; a short preStop sleep lets the endpoints update before the server stops.
  • → 2: each loop drains: HTTP finishes in-flight requests, the consumer finishes its batch, the relay publishes what it claimed.
  • → 3: close the pool, exit 0. The playhead shows it finishing well before SIGKILL at 30 s.
// observability

Logs to explain, metrics to detect, traces to locate. Alerts page on symptoms.

logs

Structured JSON, one event per line. Every line carries request_id, org_id, user_id from the MDC. Errors log the throwable. No tokens, no PII you don't need.

Answers: what happened to this request?

metrics

Per endpoint and per consumer: rate, errors, duration as p50/p95/p99. Plus saturation: pool in use, executor queue depth, queue age, DLQ size, outbox lag.

Answers: is the service healthy right now?

traces

One trace id across the API, the database call, the vendor call and the consumer that picks up the event. OpenTelemetry, propagated in headers and in the message.

Answers: where did the time go?

Page on symptoms, not causes

Error rate over 1% for 5 minutes, p99 over the SLO, DLQ not empty, queue age over 10 minutes, oldest unsent outbox row over 5 minutes. Not "CPU is 80%".

Every alert has a runbook and a person

An alert nobody acts on gets muted within a month. Fewer alerts, each one real. SLO burn-rate alerts beat fixed thresholds once you have SLOs.

hirespartan.io
  • → 1: what pages. Outbox lag is the answer to the 3 a.m. graph: when the relay dies, the queue is empty and healthy; only the outbox table shows the problem.
  • Metric: now() - min(created_at) where sent_at is null. Cheap query with a partial index on unsent rows.
  • → 2: runbooks and owners.

// what review will send back

Ten reliability mistakes review sees most

dual
write

A queue send or email after the commit, outside any outbox. Lost on the first pod restart.

launch
{ }

Fire-and-forget work in a coroutine nobody tracks. It dies silently with the pod.

ack
first

Deleting the message before the work commits. A crash in between loses it for good.

no
dedupe

A consumer that assumes each message arrives once. The second delivery sends the second email.

batch
stops

One bad message throws out of the loop and the other nine wait forever.

no
timeout

A vendor client with the default timeout, or an inner timeout longer than the outer one.

retry
everywhere

Retries at every layer, or on calls that aren't safe to repeat. One click, 27 calls, two charges.

no DLQ

A queue with no dead-letter queue, or one nobody is alerted on. Poison messages loop or vanish.

silent
relay

No alert on outbox lag. The relay dies, the queue looks healthy, nothing goes out.

no
context

Log lines without request id or org id. "Something failed" with no way to find out what.
